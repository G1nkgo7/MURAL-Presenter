# ppt-skill

生成 HTML 幻灯片演示文稿。每一页是一个独立 HTML 文件,画布 **1600×900(16:9)**。视觉风格**按 brief 从风格库挑定**(`references/design-styles.md`,74 风格 / 22 色调 / 29 主色;简约只是其中一种)——让风格服务于主题与受众。

这是**多 Agent 工作流**:你是**编排器**——做调研、全局规划、设计系统、每页规划、配图,然后调用 **subagent** 把每一页**并行**委派给 **slide subagent**(subagent 写、渲、自纠该页 HTML),最后做一次全局复审收尾。

> 不同框架里启动 subagent 的工具名不一样(`delegate_task`、`task`、`spawn`、`run_subagent`…)。本文档统一叫它「调用 subagent」——用你当前环境实际提供的那个 subagent 工具即可。

## 边界(先读这个)

- **自主推进,不提问。** 除非硬性阻塞(权限 / 登录 / 缺输入文件),否则不向用户提问、不等确认;自行补齐合理假设,做有品味的决定,继续执行。
- **页面 HTML 由 subagent 写,你绝不自己写或改。** 你只写规划文件、`base.css` 和配图;`slides/slide_NN.html` 一律经 subagent 产出。**即使是跨页统一的小改动也不例外**:跨页**视觉**统一(配色 / 字体 / 顶部 meta 样式)改 `base.css`,跨页**内容**修正带 note 重新委派受影响的页。你对 `slides/` 的 `write`/`edit` 会被直接拒绝。
- **图表是代码,不是图片。** 数据图表一律用 ECharts 在 HTML 里手写;`image_generate` 只用来生成照片 / 插画类视觉,绝不用它伪造图表。

## 工具

**编排器用:**

- `read` —— 读 brief / 参考文件(只读文本)。
- `web_search` / `web_fetch` —— 调研,可**搜文也可搜图**(找事实、数据,或找可参考的视觉 / 素材)。
- `image_generate` —— 生成照片 / 插画类配图,返回 `assets/` 下的**确切路径**(形如 `assets/img_01.png`,不用于图表)。
- `write` / `edit` —— 写规划文件和 `base.css`(**不能写 `slides/` 下的页面**,会被拒)。
- **subagent 工具**(框架不同名字不同:`delegate_task` / `task` / `spawn` …)—— 并行委派 slide subagent,尽量一次委派全部页;每个 subagent 返回一段含截图路径的简短总结。
- `vision_analyze` —— 看截图(`read` 看不了图),用于全局复审。

> 编排器**不渲染、也不执行命令**,因此无法触碰 `slides/`(守住"不写页")。要刷新某页视觉只能改 `base.css` 后**重新委派**那一页。

**slide subagent 用:**

- `read` —— 读规划和 `base.css`。
- `write` / `edit` —— 写本页 HTML。
- `bash` —— 执行 shell 命令;**用它跑渲染脚本**(见下「怎么渲染」)。
- `vision_analyze` —— 看自己的截图自检。

> **怎么渲染(用 `bash` 跑 skill 自带脚本,不依赖宿主有 render 工具)**:把某页 HTML 渲成 PNG,就用 `bash` 执行:
> ```
> python skills/ppt-skill/scripts/render.py slides/slide_NN.html renders/slide_NN.png
> ```
> 脚本自处理依赖(无头 Chromium、LD_LIBRARY_PATH、等字体就绪防豆腐块),成功后把 PNG 路径打到 stdout。**渲完用 `vision_analyze` 看那张 PNG**(`read` 看不了图)——这是你"看见"页面的唯一方式。

## 工作区布局

```
plan/
  deck.md            # 全局规划
  slide_01.md        # 每页一份规划
  slide_02.md ...
base.css             # 设计系统:所有颜色 / 字体 / 间距 token
assets/              # 配图:image_generate 产物或已有素材
slides/
  slide_01.html      # 每页一个 HTML 文件(由 subagent 写)
renders/
  slide_01.png       # 渲染截图,文件名对齐页号
  slide_02.png ...
```

所有路径都是**相对路径**,根落在本次运行的工作区,按此布局读写即可。

**渲染产物统一放 `renders/`**,文件名与页号对齐(`slide_NN.png`),每次重渲覆盖同名文件——不要把截图散落在 `slides/` 或工作区根目录。`render.py` 的输出路径就指向这里,`vision_analyze` 用它。

## 设计规范

- **整体服从选定的风格。** 全套一致地执行你在规划里定的 风格 + 色调 + 主色(见 `references/design-styles.md`)。无论哪种风格,通用底线都成立:层级清晰、每页只讲一件事、留白与重心有节奏、调色板收敛(用主色 + 少量辅助,别失控);用色强弱跟着风格走(简约就克制,波普 / 国潮就大胆,但仍守住选定的调色板)。
- **只用 token,绝不写裸 hex。** slide HTML 引用 `base.css` 的 CSS 变量(`var(--ink)` …)。`base.css` 定义一套真正的 token:`--bg`、`--accent`、`--ink`、辅助色、字体、间距。
- **⚠️ 奶油 / 米黄 / 暖白底是被严重滥用的"安全牌",默认就别用它。** 数据里近一半 deck 都偷懒用了暖奶油底 —— 这是头号雷同。**动笔前先问:这个主题最该是什么底?** 然后让背景跟着**风格 + 色调**走:
  - **商务 / 科技 / 数据 / 金融 / 政务 / 奢侈 / 暗黑极简 / 赛博** → 优先**深底**(深蓝黑 / 近黑 / 深墨绿),利落有力;
  - **医疗 / 科研 / 法律 / 冷色调** → 冷白蓝 / 冷灰;
  - **高对比 / 包豪斯 / 杂志** → 纯白或纯黑;
  - **奶油 / 暖白只留给真正偏暖的**:生活 / 文教 / 手作 / 婚庆 / 母婴 / 餐饮等;别的主题用到暖白要有明确理由。
  目标是让背景在「暗 / 冷 / 高对比 / 暖白」之间**真正铺开**,而不是清一色奶油。
- **全套只用一个背景模式。** 要么亮底、要么暗底:封面 / 过渡页可以用**同一色系的更深 / 更浓变体**做戏剧感,但**绝不在亮底和暗底之间来回跳**——暗底封面配亮底正文那种"两个 deck"的割裂感,就是这么来的。
- **调色板封闭:任何颜色都必须来自调色板,包括状态色。** `base.css` 要把**这套 deck 会用到的所有颜色**一次定全——含**涨跌 / 正负 / 警示 / 提示**这类状态色(如 `--up`/`--down`/`--warn`/`--note`),且这些状态色要**和选定主色调和**(从主色 / 辅助色派生的深浅、或同色系的暖冷偏移),而不是直觉里的大红大绿大粉。**严禁**为了"负数 / 风险 / 提示"就硬塞一个调色板外的红 / 粉 / 绿(例:导航金 deck 里冒出 `#FBEFEF` 粉底免责条、或鲜红的 `-12.5%`,就是出界)。表达涨跌优先用:箭头 / 正负号 / 位置 + 调色板内的深浅或单一强调色;免责 / 提示条用主色的淡色调(如金色 deck 用米金淡底),不要粉不要红。
- **图表是代码。** 数据图表用 **ECharts** 在 HTML 里手写,**整套配色(系列色、坐标轴、网格线、文字、标注)全部取自 base.css 的 token**——绝不用 ECharts 默认调色板,也不混入调色板外的颜色;容器给显式宽高;不要用图片伪装图表。
- **配图用 `image_generate` 或已有素材,且配色要进调色板。** 需要照片 / 插画时,编排器在规划阶段生成——**提示词里写明 deck 的主色 / 色调 / 情绪**(如 "navy and muted gold palette, editorial, low-saturation"),让出图就贴合主题色;生成后**核对配色是否落进调色板**(`vision_analyze` 看一眼),跑色就改提示词重生成,或用 CSS 给它压一层主色调(duotone / 半透明色罩)收进调色板,**别让一张五颜六色的图破坏整套**。`image_generate` 返回**确切路径**(形如 `assets/img_01.png`),把它**原样**写进该页规划,子 Agent 以 `../assets/img_01.png` 引用(不要自己编文件名);子 Agent 若发现图缺失/对不上,可 `read("assets")` 列目录核对。纯几何 / 抽象视觉优先用 CSS 形状、渐变、SVG。
- **文字精炼** —— 用短语不要整段;1600×900 装不下密集长文,会溢出。
- **中文字体必须显式命名。** 渲染环境**已本地安装 Noto Sans SC / Noto Serif SC**,所以中文 deck 的正文 / 标题 `font-family` 必须显式带上 `"Noto Sans SC"`(或 `"Noto Serif SC"`),如 `font-family: "Noto Sans SC", sans-serif;`——否则可能落到无中文字形的字体上渲染成豆腐块(□□□)。`base.css` 里再加一条 Google Fonts 的 CDN `@import` 作可移植兜底(本地已有字体,不联网也能渲染,所以别把 CDN 当唯一依赖)。
- **避免 AI 味(AI-slop)**:不用 Inter / Roboto / 系统默认显示字体,不用千篇一律的靛蓝 `#6366f1` / 紫配白,不要什么都居中,不要一排排一模一样的卡片,不要无意义毛玻璃;相邻两页不复用同一种版式。

## 流程

### 阶段一 —— 规划(你自己做)

**顺序很重要:先把材料备齐,再动笔规划——`调研文本材料` → `搜索/生成视觉素材` → `写规划`。** 这样规划才能引用你**真正拿到**的素材,而不是先写死再回头凑。

1. **吃透 brief**:主题、受众、目的、语言、调性、页数(若未给,自定 ~5–12 页)。
2. **调研文本材料**:需要时事 / 数据 / 事实时,`web_search`(搜文)→ `web_fetch` 最佳来源。把要用的事实、数字、引述先收拢。
3. **搜索 / 生成视觉素材**:确定视觉方向后,`web_search`(搜图)找参考,需要照片 / 插画时用 `image_generate` 生成,存到 `assets/`。**每搜到 / 生成一张图,都要回头检查它是否符合主题与调性**(画面内容对不对、风格搭不搭、有没有跑题或怪异元素);不符合就改提示词重生成 / 换图,**绝不硬用跑题或低质的图**。把确认可用的素材的**确切路径**记下来,供下一步规划引用。纯几何 / 抽象视觉留到写页时用 CSS / SVG,不必在这步生成。
4. **写 `base.css`**:把设计系统写成 token(视觉的唯一真相来源)。中文 deck 在此引入中文 web 字体。
5. **写 `plan/deck.md`**:主题 / 受众 / 目的 / 语言;**风格方向 —— 必须先 `read skills/ppt-skill/references/design-styles.md`,然后从三个表里"点名"各选一项写进 deck.md**(不是凭感觉造,是从库里挑):
   - **设计风格**:从 74 种里选一个,写名字(如「暗黑极简」「党政/党建」「高端奢侈」)。
   - **色调**:从 22 种里选一个,**写名字 + ID**(如「深色/暗色系(ID 1)」「黑金(ID 8)」「冷色调(ID 4)」「高对比(ID 5)」)。**这一项直接决定背景**——别滑回「浅色/暖白」默认;商务/科技/数据/政务/奢侈这类就该选暗 / 冷 / 高对比 / 黑金那几档。
   - **主色**:从 29 种里选一个,**写名字 + 它的确切 hex**(如「克莱因蓝 #002FA7」「墨绿 #1B5E20」「金色 #FFD700」);`base.css` 的 `--accent` 就**直接用这个 hex**,`--bg` 按上面选定的色调定。
   再写一句话情绪、设计规格摘要(`--bg` / `--accent` hex / `--ink` / 字体);**页序** —— 每页一行 `slide_NN:页型 — 一句话总结`(页型从下面词表选),构成清晰叙事弧线;总页数;关键事实或假设。
6. **每页写一份 `plan/slide_NN.md`**,开头必须有两行:**页型**(从词表里选一个)和**一句话总结**(这页讲的一件事);再写标题、内容要点、视觉方案——`image:`(第 3 步备好的素材**确切路径**)或 `chart:`(ECharts 类型 + 实际数据)。需要数字而 brief 没给时,改成概念图 / 流程图 / 对比结构,或明确标注示意。

**页型词表(规划时每页必须从中选一个):**

| 页型 | 页面任务 |
|---|---|
| 封面页 | 呈现主题、演讲者、场合与日期,确立整体基调并建立第一印象 |
| 过渡页 | 标示新章节或叙事阶段的开始,承上启下,提示听众当前所处位置(版式从简,仅含章节名/主题) |
| 开场页 / 引入页 / 背景页 | 借由问题、事实、数据、场景或趋势引入主题,阐明其重要性与听讲理由 |
| 目录页 | 列示内容结构与各部分顺序,建立整体框架与听讲预期 |
| 问题页 / 痛点页 | 界定当前的矛盾、困难、机会或挑战,为后续观点与方案确立必要性(仅陈述问题,不涉及解决方案) |
| 观点页 / 结论页 | 直接提出核心判断、主张或结论,以一句话明确表达立场 |
| 逻辑分析页 | 拆解原因、结构、机制或层级关系(流程图、因果、矩阵、架构、逻辑树等),阐明"为何如此"或"如何运作" |
| 数据页 | 以图表与数据佐证结论、支撑判断(ECharts),重在论证而非罗列 |
| 案例页 | 借助具体案例(成功、失败、竞品或用户故事)增强理解与说服力,并提炼其说明价值 |
| 方案页 | 阐明具体做法——策略、方法、路径、功能或行动,并回应前述问题与目标 |
| 计划页 / 时间轴页 | 呈现执行节奏:阶段划分、里程碑与时间节点,明确各阶段的产出 |
| 对比页 | 在统一维度下进行比较(方案、前后、自身与竞品),提炼差异并给出判断或建议 |
| 总结页 | 将核心观点凝练为数句,突出重点,形成明确的认知落点与记忆点 |
| 行动页 / 结束页 | 提出下一步行动或决策事项,或以呼吁、愿景、致谢、答疑、联系方式收束全篇 |

页型决定该页的版式与视觉重心(数据页以图表为主、对比页采用并列结构、过渡页力求简洁),相邻页应尽量切换页型,避免连续使用同一种。

**硬约束:最后一页不得出现任何含"聆听"的字样。**

一份 slide 规划必须**自包含**:subagent 只凭 `plan/deck.md` + `plan/slide_NN.md` + `base.css` 就能做出这一页(它看不到兄弟页)。把这一页需要的一切都写进它的规划。

7. **规划自检(委派前过一遍,有问题先改规划再委派)** —— 委派后每页要渲染自纠,代价高;规划期的问题在这步一次性堵掉:
   - **设计系统**:`base.css` 的 token 定全了吗(`--bg`/`--accent`/`--ink`/辅助色 + **状态色 `--up`/`--down`/`--warn`/`--note`**,且都和选定主色调和)?中文字体引入了吗?主色 / 背景 / 文字对比够吗?
   - **调色板 / 风格**:风格 + 色调 + 主色是不是**从库里点名选的**(色调写了名字+ID、主色写了名字+确切 hex,不是凭感觉造)?`base.css` 的 `--accent` 用的就是选定主色的那个 hex 吗?状态色没有出界的红 / 粉 / 绿?
   - **背景**:背景是不是**严格跟着选定的色调走**?有没有**又滑回奶油 / 暖白默认**(选了暗/冷/高对比色调却还是亮奶油底,就是没执行)?整套是不是**一个背景模式**(没有暗底封面 + 亮底正文那种明暗乱跳)?
   - **叙事**:页序构成清晰弧线、首尾完整(有封面、有总结 / 行动)?**页型有变化、相邻页不重复同一种**?
   - **每页规划**:每份 `plan/slide_NN.md` 都有"页型 + 一句话总结"两行?视觉方案只用 CSS / SVG / ECharts / 已备素材?缺数字处已标"示意"?
   - **素材**:生成的配图都已核对**符合主题与配色**?路径**原样**写进了对应页规划?没有引用不存在的图?
   - **自包含**:随手抽一份 `slide_NN.md`,只凭它 + `deck.md` + `base.css` 能不能独立做出这一页?

   哪条不达标,就先 `edit` 规划文件 / `base.css`、或重生成素材,**改好再进入阶段二**。

### 阶段二 —— 并行委派

规划文件和配图都就绪后,调用 subagent 工具把全部页**并行**委派出去(尽量一次委派全部,每个 subagent 负责一页,传入页号)。

每个 slide subagent 各自写 `slides/slide_NN.html`、用 `bash` 跑 `render.py` 渲染、`vision_analyze` 看截图按清单自检,返回一段含截图路径的简短总结。

slide subagent 写页要求:链接 `<link rel="stylesheet" href="../base.css">`;颜色全用 token,标记里绝不写裸 hex;ECharts 容器给显式宽高;中文文字落到引入的中文字体;不用入场动画(加载即完整态,防截到半截);不留占位 / 空框 / 破图;CSS 取负函数值用 `calc(-1 * clamp(...))`,绝不写 `-clamp(...)`。

#### 自检要求(slide subagent 必做)

**必须看图,不看代码。** 写完先用 `bash` 跑 `render.py` 渲染,再 `vision_analyze` 看截图本身——只读 HTML 不算自检,很多问题(溢出、豆腐块、破图)只有渲染后才暴露。每改一次必须重渲重看,不能凭记忆判断改没改好。

**判据分两级:**

- **硬伤(必须修掉才算过):** ① 溢出 / 出血——任何内容越过 1600×900 边界或容器边,出现多余白条黑条;② 遮挡——文字 / 图表 / 图片 / 形状互相压盖;③ 占位残留——空框、占位文字、缺轴 / 缺图例 / 缺标签的半截图表;④ 破图破表——`<img>` 或 ECharts 没真正渲染出来;⑤ 中文豆腐块(□□□)——字体没加载上;⑥ 可读性——文字在其背景上对比不足、看不清;⑦ **配色出界——图表 / 卡片 / banner / 配图里出现了调色板外的颜色**(如导航金 deck 里冒出红 / 粉 / 绿、或图表用了 ECharts 默认色),一律换回 base.css 的 token。
- **软伤(还有余量再修):** 对齐与网格、留白是否均衡(别太挤也别大片空)、层级、是否填满画布无大片死区、配色 / 字体是否贴合 deck 风格。

**循环纪律:** `edit → bash 渲染 → vision_analyze` **最多 3 轮**。每轮只做能压掉硬伤的**最小修改**。硬伤清零优先于软伤;3 轮后若仍不完美,**保留当前最好的一版**,不要无限修。

**收尾总结**必须如实报告:该页画了什么、**状态(通过 / 还剩哪些问题)**、最终截图路径 `renders/slide_NN.png`。有未解决的硬伤要写出来,别谎报通过——编排器的全局复审要靠这个判断哪页需返工。

### 阶段三 —— 全局复审

对要看的页 `vision_analyze(path=…)`(用总结里的截图路径)。横向扫整套:配色 / 字体是否漂移、**背景是否全套统一(没有暗底封面 + 亮底正文的明暗乱跳)**、**有没有页面的图表 / 卡片 / banner / 配图用了调色板外的颜色**(出界的红 / 粉 / 绿、ECharts 默认色、跑色的生成图)、有没有两页几乎雷同、叙事是否断层、页码是否缺失或错乱、**整套是否守住选定的风格 / 色调 / 主色(全套一致)**。发现出界配色:若是 base.css 的状态色没定全 / 定得不对 → 改 `base.css` 补齐和谐的状态色再重新委派;若是个别页乱用颜色 → 带 note 重新委派那一页。

修问题时**绝不自己动 `slides/` 的 HTML**(会被拒),按问题类型走:
- **跨页视觉统一**(配色 / 字体 / 间距等 token 漂移)→ 改 `base.css`,然后**重新委派**受影响的页(subagent 会基于更新后的 `base.css` 重渲并复核);你自己不渲染、不改页;
- **某页内容 / 结构 / 局部问题** → 调用一个 subagent 重做那一页,带 note 传入具体修改点(注意:重新委派会让 subagent 按规划**重写**该页 HTML,只在确有内容问题时才用)。
