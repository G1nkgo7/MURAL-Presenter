# 演示文稿不是一摞页面

## 介绍 MURAL：一种面向长程演示文稿完整生命周期的创作框架

做一套演示文稿，通常不是从新建空白页开始，也不会在最后一页出现时结束。真正的制作过程要更早一些：
先弄清这场演讲要解决什么问题，谁会听，以及希望听众带走什么。随后才是整理已有材料、核验事实、寻找图片、
规划叙事和确定设计方向。页面完成后，还要从头到尾读一遍整册，检查定义有没有变化、章节衔接是否突然、
同一种颜色是否在不同页面表达了不同含义。很多演示文稿交付后仍会继续修改，有时只改一处，有时要反复几轮。

现有演示文稿 Agent 已经能完成这个过程中的不少局部任务：列提纲、查资料、写单页、生成代码，或响应一个明确的
局部修改。更难的是让一项决策在整条链路中持续有效。开场提出的术语可能隔了十几页才再次出现；一种颜色一旦被
赋予语义，后面的图表就需要延续它；结尾可能要回答二十页前提出的问题；一个看似局部的修改，也可能悄悄改变几张
关联页面。

这就是本文所说的 long-horizon authoring。这里的 horizon 不只由页数或生成时间决定，而是事实、叙事承诺、
设计规则与用户要求，需要跨越阶段、页面和修改轮次保持有效的距离。

MURAL 的全称是 Multi-Agent Unified Revision-Aware Authoring。它是一个面向可编辑 HTML 演示文稿的
技能驱动多智能体框架，围绕 shared deck blueprint、页面组共同负责、两级渲染检查和按影响范围执行修改来组织
完整生命周期。

## 整册和单页之间，缺少一个责任单元

组织一个演示文稿 Agent 系统，最直观的方式有两种。可以让一个 Agent 从头做到尾，这样整项工作只有一个负责者，
上下文也保持连续，但轨迹会不断累积研究材料、规划决策、工具反馈、页面代码、渲染检查与后续修改。也可以按功能
或页面拆成多个 Agent，专业分工和并行执行更容易，代价是跨页关系要依赖不同上下文之间的状态传递与后续验证。

这两种拓扑都不是天然错误，它们只是把责任放在不同位置。

MURAL 在整册和单页之间增加了页面组。只要几张页面共享同一个叙事职责、视觉家族、素材系列或显式依赖，就可以
交给同一个 Group Agent。封面和结尾即使不相邻，也可以作为一组首尾呼应的 bookends；一段连续论证可以共享
生产者；所有章节过渡页可以按照同一套视觉系统制作。每一页只属于一个完整且不重叠的页面组，不同组仍然能够并行。

Group Agent 不只是一次生成几个文件。它会先写完本组全部页面，再联合渲染，查看组联系表，合并可观察的问题，
修改受影响的页面，并用最新像素复验。页面组共享的是设计 DNA 和叙事责任，而不是一套固定几何模板。组内页面需要
相互关联，但不能变成彼此复制。

![三种页面生产拓扑](../assets/figures/execution-topologies.png)

这个差别很关键。把完整 deck context 复制给每一个逐页 Agent，并不会自动为跨页关系建立共同负责者；assembly
也不是 MURAL 独有的环节，所有并行系统最终都要汇合页面。MURAL 改变的是关联内容在哪里被共同生产，以及页面汇合后
在哪里恢复整册验证。

## 把生命周期写成可执行 Skill

MURAL Authoring Skill 描述阶段、角色、落盘产物、质量门和继续执行的路径。流程从用户需求与可选材料开始。
Material 将附件整理成带位置依据的说明，使后续 Agent 不需要反复打开原文件。只有外部事实或未解释术语会改变
演示文稿的结论时，才启动 Research。这让资料接地成为一个有目的的判断，而不是所有任务都要经过的仪式。

Orchestrator 随后确定受众、沟通目标、叙事弧、术语、设计方向、页面地图、素材策略和 production groups。
这些整册决策会写入 shared deck blueprint，再编译成 group/page briefs。下游 Agent 不必从不断增长的对话中
重新猜整场演讲，只需要接收与自身职责相关的状态。

整册需要位图时，MURAL 会在页面组开工前安排一次统一 Image 阶段。这个设计看起来简单，却能避免不同页面组重复
搜索、争用 catalog，或各自生成互不相干的图片系列。Image 阶段负责把全册素材解析为一套可用的本地资产；
Group Agent 仍然决定图片如何参与最终构图。

页面组制作关闭第一层视觉循环。每个 Group Agent 完成整组首稿，渲染组图，检查最新像素，合并问题，修改后再次
渲染。所有组完成后，确定性 assembly 生成权威整册与 contact sheet。Whole-deck Review 再检查任何单组都无法
完整判断的关系，包括数值口径、术语、setup/response、视觉语义、章节节奏、特殊页面，以及页面和讲稿之间的配合。

因此，MURAL Authoring Skill 不是一套换了名字的 prompts。真正可复用的对象是创作程序：哪个角色负责哪项决策，
哪些状态需要落盘，什么时候像素才算证据，以及发生失败或修改后从哪里继续执行。

## 修改不是生成结束后的附加功能

一套演示文稿只有能够继续修改，才真正具备使用价值。MURAL 按请求的实际影响范围进行路由。一个可以精确定位的
局部请求只修改单页并重新渲染；改变几张关联页面关系或共同视觉语言的请求，会重新激活对应页面组；需要新事实或图片
时，只补充必要的 Research、Image 与受影响页面组；只有当请求改变章节、标题结构、页数、共享设计规则或多个页面组时，
系统才重新规划整册。

这里并不是要不惜代价地追求最小修改，而是选择能够可靠保持整册决策的最小范围。当影响边界不确定时，revision router
会向上升级。这样，后续修改仍然是原 authoring 过程的延续，而不是另一套彼此无关的补丁机制。

我们的训练假设也来自同一个观察。生成轨迹本身已经包含多轮 inspect、diagnose、patch 与 rerender，这些行为可能
在没有单独 edit-only 训练集的情况下迁移到生成后的修改任务。不过，这仍然是一个需要实验回答的问题。只有控制基础模型、
训练数据和运行流程，并移除 refinement 轨迹进行对照，才能判断收益到底来自哪里。

## 为什么把 HTML 作为创作源

图片式页面可以拥有丰富的第一眼效果，但它把文字、布局和图形一起压成了像素。改一个数字、移动一处标注、保留可选择文字，
或增加交互，往往需要重新生成或重建结构。MURAL 保留 HTML、CSS、SVG、文字和媒体的结构化源，同时把浏览器渲染结果
作为视觉检查的依据。

这种表示方式在生成和修改之间搭起了一座直接的桥。Agent 可以定向修改一个元素，重新渲染，再检查真实结果；后续也可以
扩展可视化编辑器和 Web 原生交互。HTML 并不意味着所有输出格式都天然等价。PPTX 导出可能损失 CSS 效果、字体、动画
或可编辑结构，PDF 与图片也有各自的取舍。MURAL 把它们视为 delivery adapters，并要求实际评估导出保真度。

## 评测真正重要的关系

单页质量仍然不可缺少，但它无法说明整册有没有兑现自己的承诺。一套页面可以张张好看，却在两处使用了互不兼容的指标口径，
忘记回答开场问题，或在中途改变颜色含义。

我们正在构建 THREAD-Bench，即 Tracking Holistic Requirements and End-to-End Alignment in Decks，用来把这些关系
变成可观察对象。计划中的 50 个 case 会分别记录过程证据、知识检查、整册要求、单页质量和 case-specific 的长程探针。
每个探针都说明一项决策在哪里建立，哪些远处目标需要消费或保持它，以及用什么可观察条件判断关系闭合。只有所有必要目标都
满足条件，一项依赖才算完成。

THREAD-Bench 不会替代已有评测。PresentBench 与 SlidesGen-Bench 提供材料接地、内容、美学和产物结构等互补指标，
DECKBench 提供多轮修改任务。把这些评测放在一起，才能判断 MURAL 是否在改善长程一致性的同时，仍然保持单页生成质量与
后续编辑能力。

## 项目现在走到哪里

当前公开的是一个 research preview。仓库已经包含项目叙事、系统配图、MURAL 品牌系统和中英文文档。Grouped workflow、
统一素材阶段、组级检查、整册 Review 和 scope-aware revision 已经出现在工作系统中，但实验代码与 Skill 仍需要冻结到一个
干净、可复现的版本。

训练集、canonical THREAD-Bench cases、Judge 校准、模型权重和正式效果结果目前尚未公开。我们选择保留这些空位，
而不是在发布页面上填入尚未稳定的数字。正式发布需要可复现配置、可追踪 run ledger、第三方再分发审查，以及适用于不同产物
的许可证。

MURAL 的出发点并不复杂：演示文稿不是一摞分别合格的页面，而是一段贯穿证据、规划、制作、复审和修改的设计论证。
系统本身也应该围绕这个生命周期来组织。
